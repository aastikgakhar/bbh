## 3. Network capture and response bodies

There is NO tool that lists network requests, keeps a history, or returns HAR-like pairs.

- `browser_wait_for_network` (bg:4688-4755): one-shot. Attaches the debugger to the session tab, `Network.enable`, resolves on the FIRST `Network.responseReceived` (after the call starts) whose `response.url` contains `url_pattern`, then `Network.getResponseBody`. Returns `{ok,url,status,method,body}`.
  - Body truncated to 5000 UTF-16 chars: `body: bodyResult?.body?.substring(0, 5000) || null` (bg:4733). Same in 1.30.2 (WS/extension/background.js:6238).
  - `base64Encoded` is dropped, so binary bodies come back as truncated base64 with no flag.
  - The body is requested at `responseReceived`, before `loadingFinished`, so large or streamed bodies often come back `null`. Body wait budget min 8 s, max 20 s (bg:597-606, 4724).
  - No request headers, request body (`postData`), response headers, timing or requestId. `method` is read from `response.requestHeaders[':method']` (bg:4732), which usually does not exist, so it defaults to `'GET'` even for POSTs (unreliable).
  - Only the session tab target; requests in out-of-process iframes and workers are probably not seen. `Network.disable` afterwards; nothing is buffered between calls.
- `browser_fetch` (bg:4757-4773): agent-originated request from the service worker, not page traffic. Returns the FULL body (no truncation in the extension; JSON-parsed when possible), `status`, `ok`. No response headers, no Set-Cookie visibility. In 1.30.1 every non-127.0.0.1 destination is blocked by the extension's own CSP (`connect-src 'self' ws://127.0.0.1:* http://127.0.0.1:*`, EXT/manifest.json:13); confirmed by the vendor (WS/CHANGELOG.md:100-102). No `credentials` option, and per the vendor 1.30.1 sent the user's cookies to 127.0.0.1 (WS/CHANGELOG.md:101-102, vendor comment WS/extension/background.js:6264-6266).
- `browser_get_page_content` returns the rendered DOM (innerText or outerHTML), capped at 30000 chars by default (bg:3348, 3374-3381).
- `browser_execute_script` can read `performance.getEntriesByType('resource')` (URLs and timings only, no bodies) or monkeypatch `fetch`/`XMLHttpRequest` in the page world to buffer bodies, which the page can see.
- Output size: the server returns `JSON.stringify(result, null, 2)` without truncation (idx:930-932). The `ws` server default `maxPayload` is 100 MiB (SRV/../ws/lib/websocket-server.js:74). The Claude Code client applies its own MCP output cap (MAX_MCP_OUTPUT_TOKENS; client side, not in this code; verify in the docs).

Conclusion for the harness: Burp is the only full-fidelity source of request/response pairs. browser-mcp cannot serve as the ingest fallback ("whichever browser MCP can return requests with bodies"): wait_for_network gives one future response with a 5000-char body and no headers; fetch makes its own request.

## 4. JavaScript execution

- `browser_execute_script` effectively always runs in the PAGE main world: the ISOLATED attempt can never compile (MV3 forbids eval in extension contexts), then MAIN world via `chrome.scripting.executeScript({world:'MAIN'})` + `new Function('return (' + code + ')')` if the page CSP allows eval, else CDP `Runtime.evaluate` in the top frame's main world, which bypasses page CSP (bg:3583-3735).
- Limits: expression only (wrapped in parentheses); top frame only; result must be JSON-serializable (`returnByValue`); a result of `undefined` is reported as failure; promises are awaited (scripting paths use an async wrapper; CDP uses `awaitPromise:true` with a 20 s cap, bg:565-571); the server gives 30 s. Code that threw or may have run is not re-run (`maybe_ran`, bg:3601-3618, 3691-3734).
- Page-world consequences: the page can observe and tamper with everything (overridden `Function`, `JSON`, `fetch`, prototypes); anti-bot sensors that hook `window.Function` can capture the agent's code on path 2. On a CSP page without `unsafe-eval`, the MAIN-world `new Function` attempt is a CSP violation, so the page's own CSP reporting (report-uri/report-to) may send a violation report to the target's collector before the CDP fallback runs (possibly with a short code sample if `'report-sample'` is set; unverified).
- `browser_select_frame` runs `new Function` in the MAIN world of a chosen frame only (no CDP fallback) (bg:5196-5234).
- Other MAIN-world injections: `get_page_content`, `get_local_storage`, `set_local_storage`, `extract_list`, `wait`, `dismiss_overlays`, `set_combobox`, `set_date` (via `safeExecuteScript`, default `world:'MAIN'`, bg:1654-1670), `scriptingClick` (bg:1586-1651), the `ask_user` overlay (bg:5185).
- ISOLATED-world injections (page cannot see them): delivery proofs `window.__bmcpTast` / `window.__bmcpHaendelse` with `allFrames:true` (bg:1444-1584).
- Page-visible artifacts left by the tool: `window.__bmcpClickTarget`, `window.__bmcpClicked`, `window.__bmcpClickListener` (transient, during clicks, bg:965-989, 1031-1036); `window.__mcpConsoleLogs` plus patched `console.log/warn/error/info` that persist until reload after `browser_console_logs` (bg:5011-5025); `#a360-overlay` and `#a360-styles` during ask_user; `data-bmcp-drop-tag` attribute during drop_file (bg:3044-3105). CDP input events are `isTrusted:true`.
- The `chrome.debugger` attachment shows Chrome's "started debugging this browser" infobar and stays attached to every tab it touched (no detach until tab close or session end; bg:486-497).

## 5. Tab identity, sessions, closing tabs

- Tabs are Chrome numeric tab ids (observed values about 1.77e9 in stored state). Sessions are keyed by the MCP server's WebSocket port (bg:15, 65-106); one Claude Code process = one server = one port = one session. Subagents of the same Claude Code process share the session and its single "active tab".
- Each session gets a Chrome tab group titled `Claude N` with a colour (bg:11, 219-254). Membership is the `tabIds` set, not the group: dragging a user tab into the group does not make it a session tab.
- Gated to session tabs: `list_tabs`, `switch_tab`, `close_tab`, every reading/acting tool (they act on `session.activeTabId`), `get_cookies`/`set_cookies` (hosts of session tabs). No `chrome.tabs.query`, no `captureVisibleTab` anywhere in bg.
- Tabs that become session tabs without being opened by the session: OAuth popups opened from a session tab whose URL contains `accounts.google.com`, `login.microsoftonline.com`, `github.com/login/oauth`, `slack.com/oauth`, `app.hubspot.com/oauth` (auto-claimed, bg:2121, 2153-2167); tabs adopted by `get_new_tab` whose opener is a session tab (which includes a tab the user opened by clicking a link inside an agent tab) (bg:5242-5268); tabs of an orphaned session with the same Claude Code pid and a dead port (bg:120-181).
- Closing without an explicit close_tab call:
  - All session tabs (including adopted popups/new tabs) are closed when the session's WebSocket drops unexpectedly: MCP server exit at chat end, crash, 4 h idle shutdown (idx:196-198), parent-chain death (idx:1406-1443), `/mcp` reconnect (releaseSession bg:256-320 via off:296-305).
  - LRU eviction closes the oldest session tab when a session exceeds 20 tabs (bg:195-217).
  - When the USER closes a session's last tab, the server is asked to release its port; no tabs are closed on that path (bg:779-783, idx:356-388, 502-514).
- Theoretical: stored `tabIds` in `chrome.storage.local` are revalidated only by existence (`chrome.tabs.get`), not identity (bg:24-63, 747-763). If Chrome ever reissued a stored id after a restart, a user tab could be pulled into a stale session. Observed ids are large, so collision is unlikely.
- Incognito: the extension is allowed in Incognito (`incognito: true` pref); `tabs.create` without a window id uses the last-focused window, which can be an Incognito window. get_cookies/set_cookies handle incognito cookie stores (bg:4811-4839).

## 8. Local listeners and trust model

MCP server side:
- `new WebSocketServer({ host: '127.0.0.1', port, verifyClient })` (idx:202-222). Ports: first free in 9876-9895, overridable with `BROWSER_MCP_BASE_PORT` / `BROWSER_MCP_MAX_PORT` (idx:45-46). Bound lazily on the first browser tool call and released after the user closes the session's last tab (idx:460-536). A plain HTTP GET gets `426 Upgrade Required` from `ws` (ws/lib/websocket-server.js:104-106); no other HTTP API; no CORS headers.
- Authentication: none. Pairing was withdrawn in 1.30.1 and `BROWSER_MCP_TOKEN` is ignored (idx:133-147).
- Origin check: the Origin header must match `^chrome-extension://[a-p]{32}$`, else 401 at the handshake (idx:214-221) and a second check in `connection` (idx:261-287). Optional pin `BROWSER_MCP_EXTENSION_ID` (idx:131, 292-296) is NOT set in this config.
- Connection choice: newest reported `hello.version` wins, ties go to the latest connection; the choice locks once a command was sent (idx:117-163, 303). Replies are accepted only from the connection the command was sent to (idx:390-403, 614-634). `terminate` needs a matching hello and the active connection (idx:356-388).
- Each command carries `pid: process.ppid` (idx:633). Heartbeat ping every 20 s (idx:455-457). 4 h idle shutdown (idx:196-198).

Who can connect to the server:
- A website: no. Browsers set Origin to the page's origin and page JS cannot change it, so DNS rebinding does not help (Origin stays the attacker origin; bind is loopback). A website can at most probe port liveness with a no-cors fetch (opaque success vs network error), subject to Chrome's Local Network Access restrictions.
- Any other Chrome extension (any id, any profile or Chromium browser): yes. Its Origin passes the regex. If it says hello with a higher version before the first command, or after the active connection drops, it becomes the active connection: it receives every command (navigate URLs, fill values including passwords, execute_script code, ask_user prompts) and can return forged results (fake page content as prompt injection). Mitigation: set `BROWSER_MCP_EXTENSION_ID=jdehgalffmffhfhmmhaokfbfnafnmgcl`.
- Any local process: yes, by forging the Origin header (non-browser clients can).

Extension side (the larger risk):
- off:142-181 + off:183-311: the offscreen document connects to ANY listener on 127.0.0.1:9876-9895 that answers 426, sends the hello, and forwards every `{method, params}` it receives to bg dispatch (off:266-294, bg:2058-2077) with no authentication of the server. Any local process (malware, a malicious npm or VS Code extension, a WSL/Docker-published port) that binds a free port in range gets full control of Chrome Profile 4: navigate any site, run page-world JS on logged-in sites, read HttpOnly cookies for any site it opens, screenshots, read local files through `file://` pages (file URL access is ON), upload arbitrary local files to a page via `upload_file`/`drop_file` (path containment exists only in the official server, idx:822-870, not in bg:5395-5404 / bg:4105-4111), and `browser_fetch` to loopback services with cookies. There is no user prompt; the visible signs are a new `Claude N` tab group and the debugger infobar.

Port collision found: Burp's MCP server is configured as SSE on `http://127.0.0.1:9876` (`~/.claude.json:1678-1681`), the base port of browser-mcp's range. Effects: browser-mcp falls back to 9877+ (stored session state shows port 9877); if browser-mcp grabs 9876 first, Burp MCP cannot bind it and the `burp` MCP client hits a WebSocket server (426), so Burp MCP looks down; the extension probes `http://127.0.0.1:9876/` every 2 s with `Origin: chrome-extension://...`, which opens and aborts an SSE request against Burp MCP each time (probably harmless noise; unverified).

## 10. Facts the bbh harness needs

- Hook matcher: `^mcp__browser-mcp__` (server key `browser-mcp`). High-risk tools to gate in PreToolUse: `browser_navigate` (url), `browser_fetch` (url, headers), `browser_execute_script`, `browser_select_frame`, `browser_upload_file`, `browser_drop_file`, `browser_set_cookies`, `browser_extract_token`, `browser_provide_feedback`, `browser_about`, `browser_ask_user`, `browser_solve_captcha`, `browser_dismiss_overlays`.
- Scope: no URL allowlist exists anywhere in the tool. The harness must enforce scope on `browser_navigate.url` and `browser_fetch.url`, and block `file:`, `chrome:`, `data:`, `javascript:` schemes (file URL access is ON, so navigate + get_page_content can read any local file).
- Deny by default: `browser_provide_feedback` and `browser_about` (target URLs and error text into a public GitHub link; INSTRUCTIONS push the agent to call them without asking), `browser_extract_token` (navigates to the researcher's own third-party dashboards), `browser_solve_captcha` (CAPTCHA automation may break programme rules), `browser_dismiss_overlays` (clicks ok/cancel/skip heuristically).
- Do not use `browser_ask_user` for secrets on target pages in 1.30.1: the target page and its third-party scripts can read the typed values and can submit the overlay themselves.
- Traffic attribution: page traffic from agent tabs is ordinary Chrome Profile 4 traffic (same `Chrome/<ver>` UA, same cookies, through Burp). It cannot be told apart from the researcher's manual browsing in that profile at the HTTP layer; the extension adds no header and has no permission to modify headers (meets the no-marker rule). Correlate by time and by the `tab_id`/URL that navigate returns. Loopback traffic (port scan, WebSocket, browser_fetch to 127.0.0.1) bypasses the proxy and never appears in Burp. `browser_fetch` (1.30.2+) requests likely carry `Origin: chrome-extension://jdehgalffmffhfhmmhaokfbfnafnmgcl` (unverified).
- Bodies: rely on Burp. `wait_for_network` = one future response on the session tab, body cut at 5000 chars, no headers, method unreliable. `browser_fetch` = full body but no headers and (1.30.1) loopback only.
- Cookies: `browser_get_cookies` returns HttpOnly values but only `name,value,domain,path`; take `Secure`/`HttpOnly`/`SameSite`/expiry from Burp `Set-Cookie` before any CSRF/CORS conclusion. Only hosts with an open session tab. Partitioned (CHIPS) cookies are probably excluded (no `partitionKey` passed; unverified). No sessionStorage or IndexedDB tool (use execute_script).
- Evaluate world: page main world in practice; returns must be JSON-serializable and non-undefined; top frame only; page can tamper; CSP violation reports may reach the target on the MAIN path.
- Screenshots: CDP PNG of the visible viewport of the session tab, no full-page option; `path` must be inside the MCP server cwd (the directory Claude Code was started in), so screenshots can go straight into `captures/`; may briefly raise and focus the Chrome window as a last resort.
- Rate: the extension has no throttle and no queue; calls run concurrently. The harness rate limiter must sit in front of browser tools too (PreToolUse), since `browser_fetch` and navigation send traffic at whatever pace the agent calls. Per-call timeouts: 30 s (ask_user `timeout+5 s`, solve_captcha 60 s, extract_list 180 s); navigate waits up to 15 s for load; text-selector fill types at 30-120 ms per char.
- Concurrency: all subagents in one Claude Code process share one session and one active tab, so parallel browser use races. Per CLAUDE.md, class-testers must not get browser-mcp tools at all; they need a private headless browser.
- Tab lifecycle: agent tabs (and adopted OAuth popups/new tabs) are closed automatically when the MCP server exits (chat end, crash, 4 h idle, reconnect). The researcher should not do manual work inside agent tabs. Max 20 tabs per session (oldest evicted silently).
- Ports: Burp MCP is on 9876, inside browser-mcp's 9876-9895 range. Recommend moving Burp MCP outside 9876-9895, or set `BROWSER_MCP_BASE_PORT=9877` (the extension still probes 9876). The bbh server must not listen on 9876-9895, and must never be a WebSocket server answering 426 in that range, or the extension will connect to it and accept its commands.
- Debugger: Agent360 keeps `chrome.debugger` attached to every tab it touched. A Layer-10 `chrome.debugger` capture extension on the same tabs may conflict (vendor comments say only one debugger client per tab; unverified for two extensions).
- Hardening options for the researcher's config: pin the server (`npx @agent360/browser-mcp@1.30.1` or a vetted local path) instead of `@latest`; set `BROWSER_MCP_EXTENSION_ID=jdehgalffmffhfhmmhaokfbfnafnmgcl`; consider turning "Allow access to file URLs" OFF (only needed for upload_file/drop_file in 1.30.2); disable the extension when not testing.
- Local data at rest: `~/.browser-mcp/feedback.jsonl` (1 line, 2026-09-01, data: URL test). `chrome.storage.local` keeps `sessions` (port -> tabIds/groupId/label/colour/pid), `actionLog` (time, method, category, session label; params no longer stored since about 1.29, bg:2016-2054), `mcpPorts`, `mcpConnected`, `mcpCount`.
